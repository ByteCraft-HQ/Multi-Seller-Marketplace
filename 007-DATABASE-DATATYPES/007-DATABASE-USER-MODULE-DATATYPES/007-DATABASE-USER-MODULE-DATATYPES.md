# USERS — Data Types Documentation

This document defines the selected SQL Server data types for the attributes in the `USERS` table, along with the reasoning behind each selection.

## Data Types and Justifications

| Attribute | Data Type | Length | Justification |
|---|---|---:|---|
| `UserId` | `BIGINT` | — | Provides a very large numeric range to support the expected growth of the system and reduce the possibility of exhausting the available identifier range. Uniqueness is enforced through the `PRIMARY KEY` constraint. |
| `UserFirstName` | `NVARCHAR` | 50 | Supports Unicode characters, allowing users to store their first names in different languages, including Arabic, English, Russian, and Japanese. The maximum length is limited to 50. |
| `UserLastName` | `NVARCHAR` | 50 | Supports Unicode characters to accommodate last names written in different languages. The maximum length is limited to 50. |
| `UserMiddleName` | `NVARCHAR` | 50 | Supports Unicode characters to accommodate middle names written in different languages. The maximum length is limited to 50. |
| `UserAccountStatus` | `VARCHAR` | 20 | Stores predefined account status values using English characters. The selected length accommodates the currently expected status values. |
| `UserCreatedAt` | `DATETIME2` | — | Stores the date and time when the user account was created. `DATETIME2` provides suitable date and time precision for recording account creation timestamps. |
| `UserDeletedAt` | `DATETIME2` | — | Stores the date and time when the account was logically deleted (Soft Delete), allowing the system to retain the user record and track when the deletion occurred. |
| `UserDeletedAtReason` | `VARCHAR` | 30 | Stores predefined deletion reason values using English characters. The selected length accommodates the longest currently defined value. |
| `UserDeletedAtTextReason` | `NVARCHAR` | 150 | Allows users to provide a custom deletion reason in different languages. The maximum text length is limited to 150. |
| `UserHashPassword` | `VARCHAR` | 255 | Provides sufficient storage space for password hashes generated by the currently intended password-hashing algorithms, while leaving room for different algorithms or configurations in the future. The application must ensure that generated hashes do not exceed this limit. |
| `UserEmail` | `NVARCHAR` | 320 | Provides storage capacity for email addresses up to the selected maximum length, while supporting Unicode data. Email format validation and normalization are handled by the application layer. |
| `UserEmailVerification` | `BIT` | — | Stores the email verification state. `0` indicates that the email has not been verified, while `1` indicates that it has been verified. |
| `UserRecoveryEmail` | `NVARCHAR` | 320 | Stores the recovery email address using the same length and Unicode support considerations as the primary email address. |
| `UserRecoveryEmailVerification` | `BIT` | — | Stores the verification state of the recovery email. `0` indicates that it has not been verified, while `1` indicates that it has been verified. |
| `UserBirthDate` | `DATE` | — | Stores the user's date of birth without requiring time information, since only the calendar date is relevant. |
| `UserGender` | `VARCHAR` | 10 | Stores the currently defined gender values, such as `MALE` and `FEMALE`, using English characters. The selected length accommodates these values. |

## Additional Notes

- `BIGINT` provides a large identifier range, but uniqueness is guaranteed by the `PRIMARY KEY` constraint, not by the data type itself.
- `NVARCHAR` is used for attributes that may contain Unicode text.
- `VARCHAR` is used for attributes whose expected values are stored using English characters.
- `BIT` represents Boolean-style states using `0` and `1`.
- `DATETIME2` is used for attributes that require both date and time information.
- `DATE` is used when only the calendar date is required.
- Application-level validation, such as email format validation and password-hashing operations, is outside the scope of this document.
- The selected lengths are based on the current requirements and may be reviewed if the requirements change.
