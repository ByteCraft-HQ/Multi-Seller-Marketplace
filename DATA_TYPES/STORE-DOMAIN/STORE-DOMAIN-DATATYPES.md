# Data Types Documentation

## 1. Store Table

The `Store` table represents stores registered in the marketplace. Each column uses a specific data type based on its purpose, expected values, business rules, and scalability requirements.

### 1.1. StoreID

- **Data Type:** `BIGINT`
- **Constraint:** `PRIMARY KEY`
- **Key Type:** Surrogate Key

**Why did we choose `BIGINT`?**

`StoreID` is the primary identifier for each store in the system. It is a surrogate key, meaning that it is generated by the system rather than derived from a real-world business attribute.

The marketplace is expected to support a potentially large number of stores as it grows. Therefore, `BIGINT` provides a large identifier range and reduces the risk of exhausting the available ID values as the database expands.

`BIGINT` is an 8-byte integer that supports values up to `9,223,372,036,854,775,807` for positive identifiers.

**Design rationale:**
- Provides a very large range of unique identifiers.
- Supports long-term growth and scalability.
- Does not depend on a store's name or other changeable business attributes.
- Can be referenced by foreign keys in related tables.

### 1.2. StoreName

- **Data Type:** `NVARCHAR(100)`
- **Constraint:** `NOT NULL`

**Why did we choose `NVARCHAR(100)`?**

`StoreName` is an essential attribute because every registered store must have a name.

We chose `NVARCHAR` because the marketplace may contain stores with names in different languages, including Arabic and other languages that require Unicode support.

The maximum length is limited to 100 characters to enforce the business rule that store names must remain reasonably concise.

**Design rationale:**
- `NVARCHAR` supports Unicode characters and multilingual store names.
- The length limit enforces the business rule and prevents unnecessarily long store names.

The 100-character limit is a business decision rather than a technical requirement. It should be validated against the marketplace's actual naming requirements.

### 1.3. StoreStatus

- **Data Type:** `VARCHAR(20)`

`StoreStatus` represents the overall administrative and operational state of a store within the marketplace system.

It determines whether the store is active, blocked, awaiting review, or in another administrative state.

**Why did we choose `VARCHAR(20)`?**

The status is represented by a short textual value. `VARCHAR(20)` provides sufficient space for the defined status values without allocating unnecessary storage for longer strings.

We use `VARCHAR` because the status values consist of predefined English identifiers and do not require Unicode storage.

**Allowed Values:**

| Status | Description |
|---|---|
| `PENDING` | The store is awaiting approval or review. |
| `BLOCKED` | The store has been blocked from operating on the marketplace. |
| `DEACTIVATED` | The store has been deactivated. |
| `ACTIVE` | The store is active on the marketplace. |
| `SUSPENDED` | The store has been temporarily suspended. |
| `DELETED` | The store has been marked as deleted. |

These values describe the store's overall state, not whether it is open or closed on a particular day.

**Important distinction:** `StoreStatus` and `StoreDayStatus` represent two different concepts and must not be treated as interchangeable.

### 1.4. StoreLogo

- **Data Type:** `VARCHAR(1000)`
- **Purpose:** Stores the URL of the store's logo.

### 1.5. StoreImage

- **Data Type:** `VARCHAR(1000)`
- **Purpose:** Stores the URL of the store's main image or visual representation.

**Why did we choose `VARCHAR(1000)` for both columns?**

Each store may have its own logo and image to represent its brand. Instead of storing the actual image files in the database, we store their external URLs.

These URLs point to image resources hosted outside the database, such as in an object storage service or a content delivery network (CDN).

**Design rationale:**
- Stores only the URL instead of the image's binary data.
- Reduces database storage requirements compared with storing image files directly.
- Allows image resources to be managed independently of the relational database.
- Provides a defined maximum length for the URL columns.

**Why not use `VARCHAR(MAX)`?**

SQL Server's `VARCHAR(MAX)` supports values up to approximately 2 GB. This capacity is unnecessary for ordinary image URLs and would allow significantly larger values than the application is expected to need.

A bounded type such as `VARCHAR(1000)` makes the intended limit explicit.

However, a length of 1,000 characters does not guarantee that every possible external URL will fit. The limit should be validated against the URL formats produced by the chosen storage provider.

**Why not use SQL Server's `IMAGE` data type?**

The SQL Server `IMAGE` data type is deprecated. It stores binary image data rather than a URL pointing to an external resource.

For this design, storing image files directly in the database would introduce unnecessary database storage and backup overhead. Using external image storage and saving the corresponding URLs is a better fit for the intended architecture.

### 1.6. StoreCreatedAt

- **Data Type:** `DATETIME2`

`StoreCreatedAt` records when the store record was created inside the marketplace system.

**Why is this important?**

The date a store is created in the system is not necessarily the same as the date the physical business was established or opened.

For example, a store may have been operating in the real world for several years before registering on the marketplace.

`StoreCreatedAt` records the system registration time, not the store's real-world establishment date.

**Design rationale:**
- Tracks when the store entered the marketplace system.
- Supports reporting, sorting, and registration analytics.
- Helps determine how long a store has been registered.
- Uses `DATETIME2` for date-and-time storage with configurable fractional-second precision.

### 1.7. StoreUpdatedAt

- **Data Type:** `DATETIME2`

`StoreUpdatedAt` records the most recent time the store record was updated.

**Why did we include this column?**

It provides a simple way to determine when the store's information was last modified without maintaining a complete audit history.

For example, if the store's name, logo URL, or administrative status changes, this column can record the latest update time.

**Important distinction:**

`StoreUpdatedAt` is not a full audit mechanism. It does not preserve previous values, identify who made the change, or record every historical modification.

If a complete history is required later, a separate audit table or an appropriate auditing mechanism should be introduced.

## 2. StoreManager Table

The `StoreManager` table represents the relationship between users with the appropriate roles and the stores they manage.

It acts as an associative table, also known as a junction table, between the user-role entity and the store entity, as described in the Relationship and Keys Documentation.

### 2.1. UserRoleID

- **Data Type:** `BIGINT`
- **Constraint:** `FOREIGN KEY`

`UserRoleID` references the corresponding record in the user-role table.

**Why did we choose `BIGINT`?**

The data type must match the referenced key's data type to maintain consistency and ensure that the foreign-key relationship can be established correctly.

Because the referenced user-role identifier is defined as `BIGINT`, `UserRoleID` in `StoreManager` must also use `BIGINT`.

**Design rationale:**
- Maintains data type consistency between related tables.
- Enforces referential integrity.
- Supports the same identifier range as the referenced key.
- Allows the relationship to scale as more user-role records are added.

The reason for using `BIGINT` here is primarily consistency with the referenced primary key. It also provides a large identifier range.

### 2.2. StoreID

- **Data Type:** `BIGINT`
- **Constraint:** `FOREIGN KEY`

`StoreID` references the primary key of the `Store` table.

**Why did we choose `BIGINT`?**

The `Store` table uses `BIGINT` for its primary key. Therefore, the corresponding foreign key in `StoreManager` must use the same data type.

**Design rationale:**
- Maintains consistency with the `Store.StoreID` primary key.
- Enforces referential integrity between stores and their managers.
- Supports the identifier range defined by the parent table.

Together, `UserRoleID` and `StoreID` identify the relationship between a user role and a store.

The appropriate uniqueness constraint or composite primary key should be defined according to the relationship rules documented in the Relationship and Keys Documentation.

### 2.3. StoreManagerStatus

- **Data Type:** `VARCHAR(20)`

`StoreManagerStatus` represents the administrative state of a specific store-manager relationship or assignment, according to the intended business rules.

It is different from `StoreStatus` because the two columns describe different entities and responsibilities.

- `StoreStatus` describes the overall state of the store.
- `StoreManagerStatus` describes the state of the manager or management assignment associated with that store.

For example, a store can remain active while one of its managers is suspended or blocked.

**Why did we choose `VARCHAR(20)`?**

The status is represented by a short, predefined textual value. `VARCHAR(20)` is sufficient for the proposed values and avoids allocating space for unnecessarily long strings.

**Allowed Values:**

| Status | Description |
|---|---|
| `PENDING` | The manager or assignment is awaiting approval or review. |
| `BLOCKED` | The manager or assignment has been blocked. |
| `DEACTIVATED` | The manager or assignment has been deactivated. |
| `ACTIVE` | The manager or assignment is active. |
| `SUSPENDED` | The manager or assignment has been temporarily suspended. |
| `DELETED` | The manager or assignment has been marked as deleted. |

The exact meaning of each state must be finalized in the business rules. In particular, the system should clarify whether blocking or suspending a manager affects only one store assignment or the manager's access across the entire marketplace.

---

## 3. Key Design Considerations

The following principles guide the data type choices in these tables:

1. **Identifier consistency:** Foreign keys must use the same compatible data types as their referenced keys.
2. **Unicode support:** `NVARCHAR` is appropriate for store names that may contain multilingual characters.
3. **Bounded string lengths:** Use explicit limits when business rules define a maximum length.
4. **External image storage:** Store image URLs rather than image binary data when images are managed outside the database.
5. **Separation of responsibilities:** Store status and store-manager status represent different business concepts.
6. **Creation and modification timestamps:** Track when records are created and last updated without confusing these timestamps with a full audit history.
7. **Controlled status values:** Enforce the permitted status values through an appropriate database constraint or reference-table design.

# Data Types Documentation — Days, Store Days, Phone Numbers, and Emails

## 1. Days Table

As explained previously, the `Days` table provides a simple but useful way to represent the days of the week.

Although the table contains very little data, separating days into a dedicated table simplifies relationships, improves consistency, and makes it easier to define store operating schedules without repeatedly storing day names throughout the database.

### 1.1. DayID

- **Data Type:** `TINYINT`
- **Constraint:** `PRIMARY KEY`

**Why did we choose `TINYINT`?**

`DayID` uniquely identifies each day of the week. Since the system needs only seven days, a small integer data type is sufficient.

In SQL Server, `TINYINT` supports values from `0` to `255` and occupies only one byte.

**Why not use `INT`?**

`INT` supports a much larger range than this table requires and occupies four bytes. Using it would provide no meaningful benefit for a table that represents only seven days.

**Design rationale:**
- Uses minimal storage for day identifiers.
- Provides more than enough values for the seven days of the week.
- Makes the intended size of the identifier explicit.

### 1.2. DayName

- **Data Type:** `VARCHAR(15)`

`DayName` stores the name of the corresponding day of the week.

**Why did we choose `VARCHAR(15)`?**

The longest English day name, `Wednesday`, contains nine characters. Therefore, 15 characters provide sufficient space for all seven English day names.

We chose `VARCHAR` because the day names are predefined by the system and are expected to be stored in English.

Unicode support is unnecessary under this specific design assumption.

**Design rationale:**
- Provides sufficient capacity for every English day name.
- Avoids allocating a larger string length than necessary.
- Supports the predefined, system-managed values.

The table should contain exactly seven valid day records, with unique identifiers and unique day names.

## 2. StoreDays Table

The `StoreDays` table defines the operating schedule for each store by associating a store with a day of the week and its opening and closing times.

This structure allows different stores to have different operating hours on different days.

### 2.1. StoreID

- **Data Type:** `BIGINT`

`StoreID` references the `StoreID` primary key in the `Store` table.

**Why did we choose `BIGINT`?**

The data type must match the referenced primary key. Since `Store.StoreID` uses `BIGINT`, the corresponding foreign key in `StoreDays` also uses `BIGINT`.

This maintains consistency between related tables and supports referential integrity.

### 2.2. DayID

- **Data Type:** `TINYINT`
- **Constraint:** `FOREIGN KEY`

`DayID` references the `DayID` primary key in the `Days` table.

**Why did we choose `TINYINT`?**

The `Days.DayID` column uses `TINYINT` because only seven days are required. Therefore, the foreign key must use the same compatible data type.

This maintains consistency between the two tables and avoids unnecessary storage.

### 2.3. OpeningHours

- **Data Type:** `TIME`

`OpeningHours` records the time at which a store opens on a particular day.

**Why did we choose `TIME`?**

The system needs to store a time of day, not a complete date or timestamp.

For example, a store may open at `09:00:00` regardless of the calendar date.

The `TIME` data type is designed for this purpose and supports fractional-second precision when required.

**Design rationale:**
- Stores time-of-day values without a date.
- Represents opening times using an appropriate temporal data type.
- Avoids storing time values as strings.

### 2.4. ClosingHours

- **Data Type:** `TIME`

`ClosingHours` records the time at which a store closes on a particular day.

**Why did we choose `TIME`?**

The reasoning is the same as for `OpeningHours`: the system needs the closing time, not a date or a complete timestamp.

Using `TIME` allows the database to store and compare time values correctly.

**Important business rule:**

The system must define how to handle stores that close after midnight. For example, a store that opens at `18:00` and closes at `02:00` the following day cannot be interpreted correctly by simply assuming that the closing time must be later than the opening time on the same day.

The implementation should also define whether closed days are represented by missing schedule records or by nullable time values.

## 3. StorePhoneNumber Table

The `StorePhoneNumber` table stores the phone numbers associated with each store.

Keeping phone numbers in a separate table allows a store to have multiple phone numbers without adding a separate column for every possible number.

### 3.1. StoreID

- **Data Type:** `BIGINT`
- **Constraint:** `FOREIGN KEY`

`StoreID` references the primary key of the `Store` table.

The data type is `BIGINT` to remain consistent with `Store.StoreID` and preserve referential integrity.

### 3.2. StorePhoneNumber

- **Data Type:** `NVARCHAR(20)`

`StorePhoneNumber` stores the store's phone number as text.

**Why did we choose a string data type instead of an integer?**

A phone number is an identifier used for communication, not a numerical value used in arithmetic calculations.

For example, a phone number may contain:
- Leading zeros, such as `01234567890`.
- An international dialing prefix, such as `+20`.
- Formatting characters, depending on the accepted input format.

If the value were stored as an integer, leading zeros would not be preserved, and the plus sign could not be stored as part of the number.

Therefore, a string data type is the appropriate choice.

**Why did we choose `NVARCHAR(20)`?**

The column allows up to 20 characters, which can accommodate many common phone-number formats, including an international prefix.

`NVARCHAR` supports Unicode characters. However, if the application accepts only standard phone-number characters, `VARCHAR(20)` would generally be sufficient because digits and the plus sign belong to the ASCII character set.

The final length and validation rules should reflect the phone-number formats supported by the marketplace.

### 3.3. PhoneNumberStatus

- **Data Type:** `VARCHAR(20)`

`PhoneNumberStatus` represents the current state of a phone-number record.

It can be used to distinguish phone numbers that are active from those that have been removed, deactivated, or otherwise restricted according to the business rules.

**Why did we choose `VARCHAR(20)`?**

The status is represented by a short, predefined text value. `VARCHAR(20)` provides sufficient space for the intended status identifiers without requiring Unicode storage.

The allowed status values must be explicitly defined and enforced by the database or application.

For example, the business rules may distinguish between an active phone number and a deleted phone-number record.

### 3.4. PhoneVerification

- **Data Type:** `BIT`

`PhoneVerification` indicates whether the phone number has been verified.

**Why did we choose `BIT`?**

This column represents a Boolean state with two possible values:

- `1` — The phone number has been verified.
- `0` — The phone number has not been verified.

SQL Server's `BIT` data type is suitable for storing this kind of true-or-false information.

**Design rationale:**
- Clearly represents a binary verification state.
- Uses an appropriate data type for a Boolean attribute.
- Avoids representing the same information using textual values such as `YES` and `NO`.

The system should update this field only according to the actual verification process, rather than assuming that a phone number is verified simply because it has been entered.

## 4. StoreEmails Table

The `StoreEmails` table stores the email addresses associated with each store.

Like `StorePhoneNumber`, it separates contact information from the main `Store` table and allows each store to have multiple email addresses if the business rules permit them.

### 4.1. StoreID

- **Data Type:** `BIGINT`
- **Constraint:** `FOREIGN KEY`

`StoreID` references the primary key of the `Store` table.

The data type must remain consistent with `Store.StoreID`, which is defined as `BIGINT`.

### 4.2. StoreEmail

- **Recommended Data Type:** `VARCHAR(254)` if the system accepts conventional ASCII email addresses.

`StoreEmail` stores the email address used to contact the store.

**Why should we use a string data type?**

An email address contains letters, numbers, and special characters such as `@`, `.`, `_`, and `-`. It is an identifier, not a numerical value, so it must be stored as text.

**Why `VARCHAR(254)`?**

A maximum length of 254 characters is a commonly used limit for email addresses. Using a bounded string type provides a clear limit and avoids unnecessarily large storage allocations.

If the marketplace intends to support internationalized email addresses containing non-ASCII characters, the encoding and validation requirements should be defined explicitly before choosing between `VARCHAR` and `NVARCHAR`.

**Design rationale:**
- Stores email addresses in a text-based format.
- Defines a practical maximum length.
- Supports email validation at the application level.
- Avoids using numeric or binary data types for textual contact information.

Email format validation alone does not prove that an address exists or belongs to the store. If ownership verification is required, it should be handled through a separate verification process.

### 4.3. StoreEmailStatus

- **Recommended Data Type:** `VARCHAR(20)`

`StoreEmailStatus` represents the current state of an email-address record, according to the marketplace's business rules.

The data type follows the same general approach as `PhoneNumberStatus`: use a short text value to represent a predefined state.

The allowed values must be defined before implementation.

### 4.4. EmailVerification

- **Recommended Data Type:** `BIT`

`EmailVerification` indicates whether the email address has been verified.

**Why did we choose `BIT`?**

Email verification is a binary state:

- `1` — The email address has been verified.
- `0` — The email address has not been verified.

The column should reflect the result of the actual email verification process.

# Data Types Documentation — Social Media

## 1. SocialMedia Table

The `SocialMedia` table stores the social media platforms supported by the marketplace, such as Facebook, Instagram, X, and TikTok.

Instead of introducing a separate numeric identifier for each platform, the system uses `SocialMediaName` as the primary key. Since the number of supported platforms is expected to remain relatively small, and platform names are meaningful identifiers, a separate `SocialMediaID` is not necessary for the current design.

### 1.1. SocialMediaName

- **Data Type:** `VARCHAR(50)`
- **Key Type:** Natural Key
- **Constraint:** `PRIMARY KEY`

**Why did we choose `VARCHAR(50)`?**

`SocialMediaName` stores the name of each supported social media platform, such as `Facebook`, `Instagram`, `X`, and `TikTok`.

We chose `VARCHAR(50)` because platform names are short textual values, and 50 characters provide sufficient capacity for the expected names.

We use `VARCHAR` because platform names are system-managed identifiers stored in English and do not require Unicode support under the current design.

**Why did we choose the platform name as the primary key instead of introducing `SocialMediaID`?**

The platform name is already a meaningful identifier. Introducing a separate numeric ID would add another column without providing a necessary benefit for the current requirements.

The expected number of supported platforms is relatively small, likely fewer than 50. Therefore, using the platform name directly as the primary key is a reasonable design choice.

**Design rationale:**

- Avoids introducing an additional identifier that is not currently required.
- Uses a meaningful platform identifier instead of an arbitrary numeric value.
- Keeps the table structure simple.
- Allows related tables to reference the platform directly by name.

The platform name must remain unique within the table. Because it is the primary key, SQL Server creates a unique index to enforce uniqueness.

**Handling platform renaming**

If an existing platform changes its name while remaining the same platform, the corresponding key can be updated.

For example, when `Twitter` is renamed to `X`, the update should change the platform name in the `SocialMedia` table and propagate to related foreign-key values through `ON UPDATE CASCADE`.

This preserves the relationship between the platform and the stores associated with it.

Adding a different platform is a separate operation. For example, adding `Facebook` creates a separate platform record rather than replacing the existing `X` record.

### 1.2. SocialMediaStatus

- **Data Type:** `VARCHAR(20)`

`SocialMediaStatus` represents whether a social media platform is currently supported by the marketplace.

For example, if the marketplace stops supporting a particular platform, its status can be changed to indicate that it is no longer available for use.

This status applies to the platform across the entire marketplace, rather than to an individual store's social media link.

**Why did we choose `VARCHAR(20)`?**

The status consists of a short textual value. `VARCHAR(20)` provides sufficient capacity for the expected status names without requiring Unicode storage.

## 2. StoreSocialMedia Table

The `StoreSocialMedia` table associates stores with the social media platforms they use.

It stores each store's social media link and the status of that specific association.

### 2.1. SocialMediaName

- **Data Type:** `VARCHAR(50)`
- **Key Type:** Foreign Key

`SocialMediaName` references `SocialMedia.SocialMediaName`.

**Why did we choose `VARCHAR(50)`?**

The data type and length match the referenced primary key. This maintains consistency between the two columns and allows the store's social media association to reference the platform directly by name.

**Handling platform renaming**

The foreign-key relationship uses `ON UPDATE CASCADE`.

When a platform name changes in the `SocialMedia` table, the corresponding `SocialMediaName` values in `StoreSocialMedia` are updated automatically, preserving the existing relationships.

This approach allows the system to use meaningful platform names without introducing a separate numeric identifier.

### 2.2. StoreID

- **Data Type:** `BIGINT`

`StoreID` identifies the store associated with the social media account.

The data type matches `Store.StoreID`, maintaining consistency with the store identifier used throughout the database.

### 2.3. StoreSocialMediaLink

- **Data Type:** `VARCHAR(1000)`

`StoreSocialMediaLink` stores the URL of the store's social media page or account.

**Why did we choose `VARCHAR(1000)`?**

Social media links are external URLs whose lengths vary depending on the platform and the specific account.

A maximum length of 1,000 characters provides a defined capacity for the expected links without using `VARCHAR(MAX)`, which would allow significantly larger values than ordinary URLs require.

The URL is stored as text rather than storing the external social media page or its content inside the database.

The selected length should be validated against the URL formats accepted by the marketplace.

### 2.4. StoreSocialMediaStatus

- **Data Type:** `VARCHAR(20)`

`StoreSocialMediaStatus` represents the state of a specific store's association with a social media platform.

For example, a store may deactivate its account or remove its social media link while the platform itself remains supported by the marketplace.

This status is separate from `SocialMediaStatus`:

- `SocialMediaStatus` describes the availability of the platform across the marketplace.
- `StoreSocialMediaStatus` describes the state of a particular store's association with that platform.

**Why did we choose `VARCHAR(20)`?**

The status is a short textual value, so `VARCHAR(20)` provides sufficient capacity for the expected status names.

### 2.5. StoreSocialMediaLinkVerification

- **Data Type:** `BIT`

`StoreSocialMediaLinkVerification` indicates whether the social media link has been verified.

**Why did we choose `BIT`?**

SQL Server's `BIT` data type is suitable for representing a Boolean verification state:

- `1` — The link has been verified.
- `0` — The link has not been verified.

Verification should reflect the result of the actual verification process. Whether the process confirms link accessibility or account ownership depends on the verification mechanism implemented by the marketplace.
